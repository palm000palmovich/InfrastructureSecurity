***Задание 3*. Повышение привилегий через системный вызов***

- Сперва напишем эксплойт /opt/vulnbackup.c:

![alt text](<../Linux_Security/screenshots/Снимок экрана 2026-09-28 в 14.06.30.png>)

Что делает программа:
getuid() и geteuid() — просто печатаем кто мы сейчас. UID — реальный пользователь, EUID — эффективный (тот, с чьими правами реально работает процесс). Когда victim запускает SUID-бинарник, UID=1001, но EUID уже 0 — ядро выставило его автоматически из-за SUID-бита.

setuid(0) — системный вызов, который подтягивает реальный UID к эффективному. После него UID=0 и EUID=0 — процесс полноценный root. Это работает только потому что EUID уже был 0 (спасибо SUID-биту). Обычный пользователь без SUID вызвал бы setuid(0) и получил EPERM (отказ).

execvp("cp", args) — заменяет текущий процесс программой cp, передавая ей аргументы src и dst. Ключевое слово — заменяет: это не запуск дочернего процесса, а полная замена себя другой программой. При этом UID=0 наследуется. execvp ищет cp по директориям из PATH слева направо — и вот здесь уязвимость. Если в PATH первой стоит /tmp/evil, найдётся наш поддельный cp и запустится с правами root.

Смысл эксплойта:
Программа vulnbackup имеет SUID-бит и владельца root. Это значит что любой пользователь, запустив её, получает процесс с правами root.
Внутри она вызывает cp по имени — без абсолютного пути. Linux ищет cp по директориям из PATH слева направо и берёт первый найденный.
Мы как victim подкладываем свой скрипт с именем cp в /tmp/evil и ставим эту директорию первой в PATH. Когда vulnbackup доходит до вызова cp — она находит наш поддельный файл и запускает его. Но к тому моменту программа уже вызвала setuid(0) и работает от root — значит и наш скрипт запускается от root.
Коротко: программа доверяет окружению пользователя (PATH) в тот момент, когда уже работает с привилегиями root. Это и есть уязвимость.
